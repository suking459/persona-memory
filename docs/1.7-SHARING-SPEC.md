# 1.7 explicit sharing and contribution origins

Implemented and locally validated; see [validation](1.7-VALIDATION.md) and [sharing guide](sharing.md). No new host/model certification.

The owner creates a dedicated shared space, then separate host/contributor bindings with explicit read/capture/review access. Private channels remain separate and copy no personal data automatically. Selective project migration still requires subject mappings, previews and review. A shared space holds one project/task subject, never a user subject; namespace/storage must reject mixed personal content. Shared claims still require review, and contributor identity is owner-assigned rather than inferred.

Policy is owner-maintained; model arguments cannot add or modify grants. Every operation rechecks it. Disabled, expired, revoked or corrupt policies deny access without stale-cache success. Read cannot escalate through arguments. This does not sandbox programs sharing arbitrary filesystem permissions.

The additional MCP service has its own name and preserves the private persona_memory service. Untested clients retain explicit limits. This first implementation is local-only, without automatic HTTP/public synchronization/multi-tenancy. Remote authentication, TLS and session revocation require separate design.

Formal origin stores space/contributor/host, stamped by the policy binding rather than tool arguments. Plain SDK origins are caller assertions, not remote identity verification. Old missing provenance stays unknown. Candidate acceptance preserves it; replacement updates it and dependency fingerprints include it. Schema 7 explicitly gates persisted origins; old-schema migration and rollback limits remain tested.

Acceptance covers private/shared coexistence, no default personal copy, two contributors reading approved project facts, separate proposal/review, non-spoofable tool origins, restart persistence, active revocation/expiry/corruption denial, role/scope/identity rejection, real-process conflicts without infinite retries/data loss, and upgrade/backup/transfer/recovery/fingerprint regression.

References: [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) and [security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices). Local stdio policy does not constitute remote HTTP authentication.
