# Upgrade to the local 2.0 candidate

Public stable remains 1.5.0. The current checkout is 2.0.0-dev.0, not a published package. Use a separately prepared local tarball for evaluation; no remote release follows automatically.

## What changes

The candidate combines scoped task handoffs, explicit local shared spaces, provenance, reviewed experience feedback/retirement, bounded scalar measurements and owner maintenance. It also changes repository prose and default generated presentation to English. Original-language records, explicit Chinese locale resources, historical compatible tag IDs and multilingual retrieval remain supported.

Schema 8 reads schemas 1–7. Published 1.0 writes schema 5 and 1.5 writes schema 6. A write from the new library can upgrade the durable snapshot. Older clients must not write the same store; do not mix package versions against shared storage. Experience metadata and shared origins are not supported by old schemas.

From 1.0, also read the [1.5 policy migration](1.5-POLICY-MIGRATION.md): default keyword-inferred emotion/health tags and relationship prose changed. Host extraction and separate candidate review remain the intended route. Existing custom rules are caller-owned.

## Safe evaluation

1. Stop writers and preserve the original store with its original package version and logical identity (persona/namespace).
2. Create an owner backup using the installed version's supported mechanism. Keep a separately verified copy outside the store.
3. Evaluate a copied store in an isolated directory with synthetic or authorized data. Do not modify daily Agent configuration just to test an upgrade.
4. Open with matching persona and namespace. Inspect doctor output, scopes, candidate status, corrected fields, expiry and original-language values. Read/import is not owner approval.
5. Persist once, restart the new client and recheck. Test recovery on a separate disposable store before switching the intended application.
6. Review any generated MCP configuration manually, including executable paths, project trust and scope. A profile is not a live-vendor acceptance result.

A full same-identity backup preserves registered dependency graphs and experience authority metadata. Selective portable exports have different semantics: they deliberately do not transfer experience verification or derived feedback authority. Do not use a selective export as a full-fidelity rollback backup.

## Rollback

Restore an untouched pre-upgrade backup to a separate, stopped store and use the matching old package. Never lower schemaVersion manually, remove unknown fields to satisfy an old parser, or let an old client overwrite a new snapshot. The actual published 1.0 and 1.5 package readers were checked against synthetic schema-8 stores: both rejected them and preserved file bytes.

## Recorded upgrade coverage

Synthetic snapshots were generated by the actual archived npm 1.0.0 and 1.5.0 packages, with archive SHA-256 recorded in test/fixtures/snapshot-1.0.json and snapshot-1.5.json. They contain corrected/superseded fields, an expired state, a separate private subject, a pending candidate, multilingual values and a legacy experience. The current tests verify exact retained record objects, pending invisibility, persistence/restart and full backup/recovery.

This is representative fixture coverage, not a guarantee for every external custom store, custom configuration or historic user dataset. Back up and inspect your own authorized data before replacing a production installation. Source/installation/platform checks do not measure model task quality.
