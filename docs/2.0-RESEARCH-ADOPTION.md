# 2.0 research adoption and implementation order

Date: 2026-11-13. Read with [research sources](2.0-MEMORY-RESEARCH.md), [evaluation](long-term-evaluation.md) and [the earlier candidate validation](2.0-VALIDATION.md). This is a follow-up to the local 2.0 candidate, not an authorization to publish or change another application.

## Delivery and ownership

Keep the dependency-free SDK and scoped local MCP service as the product. Owner CLI handles review, impact previews and recovery. Optional host-specific connectors, skills and hooks improve the user workflow around those entry points. A skill supplies procedural guidance; only the runtime implements durable state and access checks.

The normal path is: authorize/bind scope → read relevant approved records → provide data context → execute with the host → confirm actual use → propose durable changes → owner/policy review → persist. Recovery and correction must work after a fresh process starts.

Native-memory coexistence has three separate authorities:

- Host instructions and permission controls: the host/project owner remains authoritative. Memory text cannot grant tools or override current instructions.
- Native personal notes: leave native stores and account controls intact. Do not scrape generated Codex/Claude/WorkBuddy files or assume their formats are public APIs.
- persona-memory records: explicit subjects, review, source references, expiry, sharing/revocation and recovery live here. The same fact should have one designated owner, with references elsewhere.

Conflicts require visible review with source/time/owner. Repetition, embedding similarity, self-rated importance and an imported file's label do not establish authority. A future native-memory importer needs explicit source/destination mapping, a read-only preview, secret checks, independent review, exclusive output and rollback. Never import a native note as an executable instruction.

## R0 — implemented in this research batch

- Ten primary papers and eight vendor-host references reviewed, with source/version/unknown boundaries.
- Independently written synthetic session traces and a local evaluator. No external benchmark data, prompts, weights, model API calls or runtime dependencies.
- Separate retrieval and rendered-context evidence metrics, complete evidence sets, explicit abstention, forbidden stale/private IDs, context budgets, durable snapshot round-trips and read-side mutation checks.
- Required cases and diagnostic challenges both appear in reports. Negative controls catch retrieving everything, partial evidence, duplicate-ID inflation, unreported context loss, budget violations, writes during reads and malformed tiers.

This implements evaluation and architecture decisions. It does not implement the functional follow-ups below or establish model answer quality.

## R1 — task-aware context selection (implemented locally)

Problem: a legitimate standing project constraint can have no lexical overlap with the current request. A single top result can also omit half the evidence needed by a question.

The [task context API](retrieval.md#task-context) combines up to four caller-supplied queries with optionally selected constraints from a single project or task. It uses the existing scope, validity, dependency and packing rules. The combined output caps standing candidates at eight and the union at 64. Each pass reports its limit omissions, and rendering reports records excluded by the shared budget. The MCP service exposes this as optional `task` arguments to `memory_context`.

The [synthetic evaluation](long-term-evaluation.md) enables standing selection on the designated task and checks the actual rendered payload. That challenge passes while the original 17 required cases still pass. Tight budgets and queries without lexical overlap remain relevant limitations. Actual host and model results are covered by R3 and R4.

## R2 — bounded consolidation proposals (implemented locally)

Problem: long interaction histories accumulate repeated or fragmentary observations; careless summarization invents identities, dates or general rules.

The [consolidation SDK and MCP tools](consolidation.md) accept an explicit owner/host-triggered batch of up to 32 approved, same-subject source references and 16 proposed summaries. Source and output budgets are fixed. Drafting is read-only and uses an application-provided callback when requested. Summaries are inferred records with exact source revisions and fingerprints. The host and reviewer must preserve speaker, time, negation and conditions in the wording. Evidence changes invalidate a pending proposal or its reviewed derivative. Original sources remain intact.

Acceptance: review/reject/revise across restarts; corrected/deleted/expired source invalidation; competing writes; duplicate and repeated-source controls; cancellation and schema round-trips. Separately measure whether a real extractor preserves negation, speaker identity, multilingual values and time. Scripted callback fixtures cannot certify this quality.

## R3 — host workflow and native-memory coexistence

Prioritize the available Codex and DSH installations. Prepare synthetic project flows in dedicated homes/configuration directories; use owner-provided login/API access only when needed. Do not copy daily credentials or alter daily profiles. Claude Code and other unavailable tools retain experimental status until actual client execution is possible; users do not need to buy or install every product.

For each claimed host, demonstrate installation/enable, native-rule coexistence, scoped read, pending capture, independent review, correction, new-process recovery, handoff, forgetting, revocation and actual tool calls. Also test current instructions taking precedence over stale recalled notes. Bundle generation or a generic MCP subprocess is not this acceptance level.

## R4 — comparable model-quality evaluation and release gate

Hold host/model/version/tasks constant. Compare memory disabled, the host's native memory, persona-memory and, where meaningful, coexistence. Record which source material each condition may access; avoid native-memory contamination between arms. Predeclare tasks/evidence and reserve unseen questions. Separate extraction, candidate recall, complete rendered evidence, answer correctness, refusal, unsafe/private retrieval, latency and provider-reported token usage. Include reviewers for ambiguous answer grading; retain disagreements.

The current scalar comparison utility can report measured numbers but cannot validate task equivalence or compute costs without actual usage/prices. Public LongMemEval/LoCoMo runs are optional later evaluations with dataset/version/license and judge setup recorded; the synthetic evaluator is not a replacement score. Do not adopt a learned ranker, semantic provider or automated consolidation default on the strength of another paper's headline gain.

The [model trial protocol](2.0-HOST-TRIAL-PROTOCOL.md) specifies isolation, paired inputs, grading and stop conditions for a future authorized run. Treat the offline evidence comparison as an engineering gate and leave answer-quality claims open until the paired model trials are complete.

## Optional casual-chat character

The [character SDK](character.md) derives temporary mood and longer-lived preferences from authorized metadata. It takes the timescale distinction from [ALMA](https://alma.dfki.de/papers/aamas05.pdf) and treats life-like expression as host behavior rather than an authority over user tasks. Its state, routing and voting rules are independently implemented. Work and ambiguous turns receive only the work-side inputs. Explicit chat turns receive a bounded projection of the character state. The host provides separate histories and handles observation approval. Cross-profile merging is deferred.

Before publication, validate the final changed source/package on the supported Windows/Linux/Node scopes, check migration/recovery and privacy/origin/dependency boundaries, and state which hosts and quality claims actually passed. Final 2.0 publication remains an explicit owner decision.

## Deliberately deferred

No automatic transcript collection, hidden background model spend, model fine-tuning, mandatory graph/vector server, learned memory gate, arbitrary knowledge-graph evolution, global identity merging, remote multi-tenant service, automatic skill promotion, native-store rewriting or complete event-sourcing rewrite. These need measured demand and separate permissions/design rather than being bundled into a small-memory component.

Source ideas are acknowledged academically. This batch adds no third-party implementation and changes no LICENSE/NOTICE or old release history. Existing origin-review limits remain in force; implementation records do not establish worldwide originality or exclusive legal ownership.
