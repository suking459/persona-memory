# 1.8 conditional experience and feedback specification

Implemented and locally validated, unpublished. Existing recordExperience remains; no task execution is added. See [interfaces/boundaries](experience-reuse.md) and [validation](1.8-VALIDATION.md).

Host-extracted task/context/attempt/result/conditions/outcome enters a candidate and needs owner review. Capture proposes unverified model reports; verified host assertions require review access. SDK labels are still caller assertions, not event authentication. Feedback candidates use helped/not-helpful/failed/not-applicable with the exact approved experience ID/revision, actual evidenceId and trialId. Reported feedback remains separate from owner-attested host-source feedback; forged value labels in generic model proposals do not acquire that authority. Approval alone does not verify a real task.

Conditions use explicit literal labels, not natural-language inference. Required labels must be included in current conditions; feedback conditions match the exact set. Missing evidence/conditions produce reasons. Adverse feedback affects matching conditions, not automatic global retirement. Owners can propose same-field retirement; acceptance excludes it from generic recall while preserving history/evidence. Correction/reinstatement requires fresh evaluation and does not copy old success conclusions.

Feedback counts deduplicate connected trial/evidence identities, prefer explicit owner attestation and expose conflicts. Counts/evidence are shown without invented accuracy/confidence. derivedFrom fingerprints invalidate support after correction/forgetting/expiry/dependency failure. Full same-identity backups retain dependencies; selective export refuses derived feedback and never transfers host verification authority through standalone experience text.

Schema 8 adds candidate experience and unverified model/lifecycle metadata, retaining old migrations/fingerprint expressions. Lower version headers cannot smuggle fields; back up before upgrade and do not use old clients on new data. Feedback uses ordinary episode JSON payloads and the existing atomic review/capacity/CAS path, not a new background database.

Acceptance: source-language preservation, model/host separation, retry deduplication, changed-condition non-generalization, positive/negative conflicts, spoof rejection, scope/privacy, invalidation, explicit retirement/history, restart/origins/roles/backups and old-schema gates. SDK/CLI/MCP tests remain distinct from actual vendor/model acceptance.
